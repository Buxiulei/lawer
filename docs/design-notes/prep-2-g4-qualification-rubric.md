## 判定树：拿到一条 G4 挂点，按序问

```
① 它是 FAIL(光秃条号) 还是 N/A(待补卡)？
   ├─ FAIL → 走 ②
   └─ N/A  → 走 ④
② 该条文在树内有 statute_quotes 吗？（查 knowledge/index.json）
   ├─ 有  → ★ 真行为问题：原文就在模型手里的卡上，它没抄 → 计入 G4 未达标
   └─ 没有 → ⛔ 断言 bug：库里没原文却判了 FAIL，应该判 N/A(pending_card)
             （这正是三分支要防的"逼模型编原文"，报 lead 修断言，不算模型的错）
③ （②判真行为后）看它落在哪：
   ├─ 六条/实施条例两条 → 最重：主路条文，注入侧引用块本就替它拼好了，仍不抄
   └─ 其它有原文的条文  → 次重：同样是行为问题，但优先级低于主路
④ N/A 的：该条文确实全库无原文吗？
   ├─ 是 → ✅ 判定正确，进补卡清单（走作业①核对栏目归类）
   └─ 否 → ⛔ 断言 bug（有原文却判了 N/A = 漏判，比误判更危险，报 lead）
```

## 三个必须分开写的结论桶

1. **真行为问题**（有原文没抄）——计入 G4 达标判断，是发版依据
2. **断言 bug**（②的"没有"分支 / ④的"否"分支）——不计入行为评价，报修
3. **待补卡**（正确 N/A）——不计入行为评价，进补卡闭环

> 混着报会重演今天的老毛病：把判据缺陷读成产品缺陷（第 15 条教训）。

  但**它同样会让用户拿不到逐字原文**——发版判断要把这块单独说清，别被"没有 FAIL"糊过去。
