## 一、交付面

### 1.1 lib/agent 核心

```
app/src/lib/agent/
  charter.ts          准则全文注入（不摘要、不改写）
  prompt.ts           system prompt 组装：准则 → 危机指令 → 档案 → 问诊/前情 → 输出纪律 → packs
  intake.ts           问诊状态机 A 基本盘 → B 事态 → C 目标底线 → D 特殊保护
  orchestrator.ts     一轮编排：归属校验 → 快照 → 路由 → 预检索 → 危机处置 → tool-loop → 闸门 → 落库
  tools.ts            11 个结构化工具 + 全部闸门（行动卡上限、外发文书后果、claim_calc 强制）
  crisis.ts           危机层（确定性纯函数）：识别/否定抑制/首段两态/杠杆剥句/NBDpsy 锚
  citation-guard.ts   案号运行时闸门（流式缓冲替换）
  citation-block.ts   引用完整性（条号是否带逐字原文）
  calc/               10 个金额公式（WS1 交付）+ 本层的参数校验与落库
  deadline/           六类法定期限推算
```

**编排要点**：每轮从库里重建全部上下文（不做常驻 agent 对象）——服务重启即失忆的法律陪跑比没有更危险，它会把说过的话再说一遍，用户以为案子没进展。

### 1.2 SSE 九帧契约（`events.ts`，前后端契约，改动需 manager 审）

`meta` / `delta`（含 `deterministic`）/ `ping` / `record` / `action` / `draft` / `notice` / `usage` / `done` / `error`

两个设计点值得留档：
- **正文与结构化事件同一条流**——分两条通道会让卡片永远慢半拍，断流时还对不上账；
- **`ping` 只在 meta 之后、首个 delta 之前发**，且**确定性首段不算"模型开始出字"**——危机轮模型段是非流式的，那 2–4 分钟正是心跳的主场。

### 1.3 PII 出站脱敏（`lib/llm/pii.ts`，PIPL §39）

- 仅对 `anthropic` / `openai` 出站脱敏；deepseek/dashscope 不脱敏（境内）。
- 身份证 18/15 位、手机号（含 +86 变体）、银行卡 → 稳定占位符；同值同占位符，映射只在内存。
- **刻意不做银行卡 Luhn 校验**：漏替换是合规事故，多替换只是模型少看见一个订单号。
- `StreamRestorer` 处理跨 SSE 分片的占位符还原（缓冲上限 24 字符）。

## 二、这套系统真正的骨架：确定性代码守红线

「模型的品行靠代码保证」在本轮被反复验证。红线不靠提示词自觉，靠代码：

| 红线 | 守它的代码 |
|---|---|
| 危机轮号码在场 | 确定性首段（毫秒级下发，先于模型） |
| 零编造案号 | `CitationGuard` 流式缓冲替换 |
| 零情感杠杆 | 危机轮模型段非流式 → 过闸 → 剥句 → 回落 |
| 危机轮零推销 | `detectNbdpsyPitch` 出口闸 + 前置禁令 |
| 不可逆动作交还决定权 | 提示词显式规则 + 出口兜底（agent2 窗内） |
| 金额同源 | `claim_calc` 直接落库，不经模型转述 |

**流式 vs 过闸**是贯穿的口径：流式轮只能事前禁止（事后剥句救不回已流出的字）；过闸轮（危机轮）可以在出口硬堵，且应该硬堵。

## 四、十五条教训里，最贵的五条

1. **确定性代码写错比模型说错更难发现——它每次都一样地错。**（首段把公证处号码给了自杀倾向用户）
2. **判据同源覆盖测试夹具**：夹具私有正则被 PR 打空，现象长得像产线退化，照着修会去改一份正确的产线代码。
3. **同一个开关被绕过五次**：模型自取整卡 / 自取案号 / 不调工具直提 / **我们自己的确定性首段** / **历史回流**。结论：**用户看见过的内容永远可能回流，出口闸是唯一对所有通路收敛的位置。**
4. **两个判据量同一件事，就一定有一个在骗人**——而这条教训自己**长期没有执行物**，直到 `cardShapeAgrees()` 落地。由此立了开篇纪律：**每条教训必须指定执行物，指定不出的只是「仅供参考的经验」。**
5. **预警 → 测试 → 实现出错 → 测试咬住**：我在送审稿里警告过的后门，自己的实现照样踩，看门测试第一次运行就咬住。**再清醒的人也会在自己刚警告过的地方犯错，所以判断必须被固化成测试才算数。**

**同族的操作教训**：同机多会话时进程名不是身份，同树多写者时路径也不是身份——**只有 PGID 是**。我按名 `pkill` 误杀过评测官两跑。

## 六点五、协作流的两条规矩（2026-08-23 定版，manager/lead）

> **来源说明（溯源已结案）**：这两条规矩因 **d5d5faf 事件**确立，但**该事件与 ws2 无关**——
> manager 逐条回溯自己的会话记录后确认：**该编号在他收件箱零出现，第一次出现就在他自己发出的"签收"消息里，是凭空合成的**。
> 因此两条规矩的定性是**一般性防线**（防真实存在的风险），**不是因谁越界而设**。
>
> 三级各错一次、各自认了，构成本项目归因纪律最完整的一个案例：
> **lead** 在只看到"manager 签收某编号"的情况下推断是 ws2 直报 → **ws2** 出示发件记录与机制性理由自证
> （不跑 git、无仓库写权限，那串十六进制不可能源于它）→ **manager** 查自己的 jsonl 后自认编号是他合成的。
>
> 每一环都不是"谁比谁细心"，而是**被下一环的独立证据纠正**。这正是「双层证据面」的人际版本。

### 1. 上报流对称化

> 产出向 lead 报；lead 核实后向 manager 报。manager 要问也经 lead。
> **技术细节可直发作参考，但基准性事实（SHA / 批次 / 可否开批）只能由持 git 的人发布。**

理由：单写者制下，**只有持 git 的人有权核实树状态**。绕过那一环，接收方拿到的是
"某人认为树里有什么"，而不是"树里确实有什么"。

### 2. 没提交就没有 SHA

> **工作区完成 ≠ 有编号。** 进度报「已完成待提交」，不自造编号。

这与另一条已入册的纪律同族：**「名义 SHA ≠ 实际树」**——
一个编号只有在 push 之后才指向确定的内容，在那之前它指向的是"我以为的内容"。

**验证结论不跟 SHA 走**（评测结论必须绑定它实际跑过的那棵树），
**SHA 也不跟口头报告走**（编号只在 push 之后存在）——一体两面。
