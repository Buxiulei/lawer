# 设计过程记录（WS2 后台技术线，2026-08-22 ~ 08-25）

> # **commit message 记得下结论，记不下当时否掉的那几个方案。**
>
> **被采纳的方案会体现在代码里，被否掉的方案不留任何痕迹；
> 而下一个人最可能重新提出的，恰恰就是被否掉的那几个——因为它们看起来合理，
> 当初我们也是这么想的。于是团队会重新走一遍已经走过的弯路，而且走得理直气壮。**
>
> **所以：设计文档的核心价值不是记录我们做了什么（那在代码里），
> 是记录我们没做什么、以及为什么不做。**
> ——manager 2026-08-25，**这是这个目录存在的全部理由**

## 本目录里"为什么不那么做"的四个例子（每一条别人明天都会重新提）

| 被否掉的方案 | 为什么不做 |
|---|---|
| 归属判定**放大窗口** | 放大是给参数找例外，**且会把邻条原文误算成本条**；改的应是判定单位 |
| 别名**改 `matches()` 打分** | 全局面波及 217 张卡；**别名落数据面，逐卡面错了只伤一张、可单条回滚** |
| 危机轮情绪卡**填满 5 个位子** | 库里情绪卡仅 13 张，**5 个位子会把它们几乎全倒进去，反过来稀释危机指令** |
| "引判例必带案号"**做成两态** | 46 张卡明示"官方案例，未公开案号"——**那不是缺料，是事实**；判 pending 等于**派人去补一个客观不存在的东西** |

## 为什么入库（判别依据，非重要性判断）

> **凡在会话级临时目录里产生的、被多方引用过的产物，必须在当次会话结束前入库。**
> **判别：如果它被第二个人引用过，它就不再是草稿。**

这条的好处是**不需要判断重要性**——"被第二个人引用过"是可观察的事实，
而重要性判断恰恰是反复失效的那种东西（"它在我脑子里的分类是报告不是代码"）。
**本目录按此通则全量入库，未做取舍**：取舍本身就是那个失效的动作。
