# 专议方案：首诊场景的核心条来源（WS2 起草，manager 参与裁定）

## 0. 设计起点（manager 定调，逐字）

> 「一个为了'不臆断'而设计的沉默，在用户最需要指引的场景里变成了失职。」
> **克制是美德，但克制到用户拿不到东西就是缺席。**

配对的约束（ws2-agent 自查句）：**不猜 ≠ 什么都不给。** 方案要在"不臆断"与"不缺席"之间给出
一条**结构化的**中间路径——扩来源，不是放开让模型自己猜。

## 1. 问题重述（本轮真因）

coreArticleKeys 三来源 = claims.basis / 行动卡 detail / deadlines.derived_from——**全部来自
已落库档案**。首诊时档案为空 → ⭐块整段不输出 → 模型没有"哪几条是核心"的信号 → 光秃。
而首诊恰是档案最空、用户最需要正确引用的时刻（第一次接触、最没判断力、马上要拿条文去谈判）。

## 2. 候选来源盘点（按"结构化程度"排序，只考虑代码可判定的信号）

| # | 信号 | 结构化程度 | 首诊可得 | 评注 |
|---|---|---|---|---|
| S1 | 档案三来源（现状） | 高 | ❌ 空 | 保留为主来源，档案建立后仍最准 |
| S2 | **本轮检索命中的 statute 卡**（facts.statute_quotes 非空的卡） | 高 | ✅ | ws2-agent 推荐主案；"注入什么就该引什么"，与第五闸口径天然一致 |
| S3 | 场景任务类（task-class）→ 预配核心条映射 | 高（人工预配） | ✅ | manager 曾提"从场景任务类推核心条"；准但要维护映射表，法条更新时人工同步 |
| S4 | 用户消息里出现的条号 | 中（正则可取） | 偶得 | 用户点名的条文应答必逐字——但作**追加**信号，不作主来源（用户可能引错） |
| S5 | 模型自选 | 无 | — | ❌ 排除：模型自我提名=把"哪条是核心"交还给猜测，违背"模型的品行靠代码保证" |

## 3. 推荐方案：S2 为主 + S3 封顶排序 + S4 追加，S1 恒优先

**规则（全部代码可判定，模型零自由度）**：
1. S1 非空 → 现状不变（档案来源恒优先，最贴案情）；
2. S1 为空 → 取 **S2**（本轮检索命中且 `facts.statute_quotes` 非空的卡的条目）为候选池；
3. 候选池按 **S3 映射表**排序（该任务类的预配核心条排前；映射表缺该任务类时按检索得分序）；
4. **上限 2–3 条**（ws2-agent 自标陷阱："⭐全部命中"不得退化为"每条都是核心"——那是绕回
   已被否掉的粗规则）；其余条文维持"可只给条号"现状；
5. **S4 追加**：用户消息中正则可取的条号若命中库内条目，**必入**⭐（用户点名的条文，
   回答必须逐字），不占上限名额但同样受库内有源约束；
6. 候选池为空（检索无 statute 卡）→ ⭐块**照旧不出现**——这不是缺席，是真无料；
   此时 G4 判定按「⭐机制不可用」态处理（判据侧已落）。

**为什么这不是"猜"**：每一步的输入都是结构化事实（检索命中、facts 字段、正则条号、预配映射），
输出是确定性函数；模型在整条链上没有提名权。"不臆断"守住了，"不缺席"也守住了。

## 4. 需要 manager 裁定的四点

1. **上限取 2 还是 3**（首诊信息密度 vs 完整性；我倾向 3，S03 型场景 2N/N+1/时效常并存）；
2. **S3 映射表要不要本期做**（不做则第 3 步退化为检索得分序——可接受的降配起点，
   映射表可列入迭代清单后补；我倾向本期不做，先上 S2+S4，少一个人工维护面）;
3. S4 用户点名条文**不占上限**是否成立（我倾向成立：用户问的必须答，这是问答基线不是核心条策略）；
4. 行为修落地后的验收口径：重跑 S03×3，⭐块非空 + §46/§40 类核心条带逐字原文；
   同时**回归 S14**（改了 prompt 组装，第五闸行为面回归必做）——重跑范围是否只这两场，请裁。

## 5. 执行物（裁定后）

- `coreArticleKeys` 扩来源实现 + 「首轮空档案场景⭐块非空」测试（ws2-agent 备忘三条测试的第 2 条）；
- charter/prompt 注释更新（⭐块语义："本轮核心依据条"来源规则写明）；
- 迭代清单：S3 映射表（若裁定后补）。
