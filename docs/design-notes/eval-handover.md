# 评测运行知识交接（ws2 → 评测官）

README 里写的是**判据设计**的教训，这份是**跑批**的教训——都是踩出来的。

## 一、批次有效性（最贵的一课）

**跑批期间任何人改了源码或知识卡，这一批就作废。** 5 连跑是 `for` 循环里每次新起
`npx tsx` 进程，**每一跑都重新 import 一次源码**。PR #30 在批次跑到一半变基入树，
五次跑的不是同一份卡——那批 2/5 的成绩单毫无意义，只能标注作废重跑。

推论：
- 开跑前确认没有别的窗口正在改 lib/agent、scripts/eval、knowledge/。
- 自己在等批次时**不要顺手改代码**，哪怕改的是别处（判断"别处"本身就会出错）。
- 批次跑完再落改动。批内一致性 > 手快。

## 二、别用 run_in_background 跑长任务

会被误杀。一律：

```sh
nohup sh -c '...; echo done > <marker>' >/dev/null 2>&1 &
```

再用 Monitor 等 marker 文件出现。日志写文件，别指望回显。

## 三、杀批次要**验证**杀干净了

有一次杀了一半，旧批次残留进程和新批次**同时在跑**，两批结果交叉写进 results/，
差点拿混着的数据下结论。

```sh
ps -ef | grep -c "[e]val-agent"   # 必须是 0 才算干净
```

注意 `sh -c` 父进程与 `npm exec` / `tsx` / `node` 是一串，杀父不一定杀子。

## 四、三类中断，处置完全不同

| 现象 | 真因 | 处置 |
|---|---|---|
| 单剧本卡死几分钟后 abort | 模型首字前思考超时 | `IDLE_TIMEOUT_MS`（已调到 240s） |
| 整场判成"运行失败" | judge 超时 AbortError 冒泡 | 已修：judge 失败→ERROR→SPLIT，**不吃掉已跑完的机械断言** |
| `terminated` / `fetch failed` | socket 抖动 | 已有有限重试（1 次），再挂就值得人看 |

**基础设施故障绝不能伪装成行为判决。** 判官挂了跟模型答错，长得可以一模一样。

## 五、红线是概率性的，一次通过不构成证据

我曾报过"S15 红线彻底全过"，随后那一跑它就编了案号。**过了一次 ≠ 守住了。**
红线一律 5 连跑，逐次记录，不许挑好看的那次报。

## 六、两个数必须分开统计

- **用户面零编造** = 红线（用户看到了编的东西）
- **模型想编被闸门拦下** = 运维信号（`【案号待核实】` 出现次数）

后者升高说明模型在变得更爱编，是预警；但它不等于红线破了。混着报会同时掩盖两件事。

## 七、成绩单要照实记，不许粉饰

- 作废的批次**就地标注作废**并写明原因，不要删掉重跑当无事发生。
- `EVAL_RUN_NOTE` 写清这一跑**没有包含**什么改动（披露比结论重要）。
- SPLIT 既不算过也不算挂，不许悄悄归进任一边。
- `scripts/eval/results/` 已 gitignore（含模型转录），**不要提交**。

## 八、断言报 FAIL 时，先看原文再改代码

`landlineMarkAssertions` 首版报 S08 轮1 FAIL，实际模型输出**完全合格**——
断言自己写错了（只查号码之后，没查之前）。同一天还有一次：测试夹具的私有正则被
PR #30 打空，现象长得像产线退化，**照着修就会去改一份正确的产线代码**。

规矩：FAIL 先 dump 原文看一眼，确认是行为问题再动手。误 FAIL 的代价不比漏判小。

## 九、常用口令

```sh
cd app && EVAL_NO_JUDGE=1 npx tsx ../scripts/eval-agent.ts S08   # 快迭代，只跑机械断言
cd app && EVAL_DUMP=1     npx tsx ../scripts/eval-agent.ts S08   # 打印回复全文（查误报必用）
cd app && npx tsx ../scripts/eval-agent.ts                       # 全量 15 场
```

开跑会**强制**校验路由未降级——降级模型跑出来的 PASS/FAIL 和正常的长得一样，
拿它签红线等于用另一个模型的表现背书。这条断言别关。
