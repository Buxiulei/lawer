# 法律智能体设计方案 · 用户旅程与陪跑优先

角度：从核心客户窗口（风闻裁员 → HR 约谈施压期）与真实用户行为出发，先定"用户在什么时刻需要被接住、被拦住、被推一把"，再决定档案、知识、推理、工具与评测各自服务什么。技术是陪跑体验的实现手段，不是目标。

论点：**好的法律陪跑 agent 不是"答得最全"，而是"在用户做出不可逆动作之前，让他做对了那一件事"。** 这个窗口里用户不需要争点分析，需要的是"现在 5 分钟内怎么说、今晚导出什么、明天早上怎么回复"；仲裁阶段以后才需要要件与争点。因此整套设计按窗口分档：S0/S1（风声/约谈中）做深，S2/S3（协商/解除）做全，S4+ 做"准备与分流"。

现状起点（据 r3 与仓库核对）：运行链十环已具备；charter §2 已把"每轮 ≤3 张行动卡"定为硬要求（`lib/agent/tools.ts` MAX_ACTION_CARDS=3）；事实卡 P0 永不降级、〔未记录〕显式化（`lib/agent/case-facts.ts`）；期限由系统算日（deadline_set）、30/7/3/1 天提醒邮件已上线（`lib/notify/deadline-reminder.ts`）；首诊按阶段种行动卡（`lib/cases/intake-actions.ts`）；十五剧本评测 S01–S15 中 S01/S02/S03 正是窗口剧本。**短板恰在陪跑闭环没闭上**：行动卡给出后无人催、无人跟踪逾期；核心六条法条无逐字原文靠检索碰运气；时间线写入无幂等；期限漏登记无告警；用户自带 agent 场景下上述纪律全靠自觉。

## Q1 目标函数：什么叫好，什么叫失败

**成功判据（每条可量化、绑到现有或新增判据）**

1. 窗口首轮当场可执行率：S0/S1 阶段首轮回复至少一张行动卡 due_at 在 24 小时内、how 含可照读原句（S01-首卡当场可执行 已有，补 due 时距断言）。目标 ≥95%。
2. 不可逆动作前置拦截率：用户表述"要签/要辞/要发/要发朋友圈"时，回复含利弊 + 决定权交还句（S03-no-01 判据反向使用）。目标 100%，红线级。
3. 期限零漏：时间线出现解除/裁决/判决送达类事件后，本轮或下一轮 deadlines 表有对应行；线上按周抽查缺口数。目标缺口 0。
4. 引用可回溯率：法条断言对应 packs `facts.statute_quotes` 逐字命中；反向指标是 citation-guard 剥句率（剥得多 = 模型在编）。目标剥句率 <2%。
5. 档案回写率：用户当轮提供的日期/金额/公司名/文件，当轮落库比例（GPT 读档事故的双写与零写都算失败）。目标 ≥90%、重复行 0。
6. 陪跑续航：行动卡按期完成回访率、7 日内二次回访率——产品指标，不进门禁，进周报。
7. 危机漏接：红线剧本 S08/S15 100%；线上 emotion_log 与 crisis_hits 抽样对比。

**失败模式清单与拦截层**

| 失败模式 | 拦截层（现有 → 补强） |
|---|---|
| 幻觉引用（编案号/条文/数字） | 知识层 statute_quotes 逐字 + `prompt.ts` EMPTY_PACK_DIRECTIVE 事前禁令 + `citation-guard.ts` 事后剥句 + eval G4；补：窗口包常驻注入（Q2） |

## Q2 知识层：卡片 + facts + 窗口包

**结构选择：卡片（现状 239 张，facts 结构化字段）为主，不建图谱。** 理由：陪跑场景的知识消费是"这一轮要引哪几条、这一步的依据是什么"，是按窗口/场景取用，不是按概念游走；图谱在没有可检索判例原文的现实下只能连法条与转述，投入产出不成比例。段落式 RAG 被否决：无法做 facts 校验（数值必须在正文逐字出现）与 CitationGuard 白名单。

**采集与结构化**：法条卡以 flk.npc.gov.cn 现行文本整篇抓取后按条号切分，`statute_quotes.text` 逐字进 facts；地方规定与解答（534 号）走单点事实源卡；数据卡必带 `effective_from`，补 `effective_to`/`superseded_by`（现只有 effective_from）；判例卡只写要旨 + 来源 URL + "官方案例，未公开案号"标注，**不整段转录商业库原文、不爬裁判文书网**（r2 合规风险）。

**窗口包（新增）**：按阶段声明"每轮必注入的核心条"，不靠检索排序。S0/S1：劳动合同法 §39/§40/§41/§46/§47/§87 + 534 号解答对应条 + 北京封顶数据卡；S3：§38/§46/§48 + 调解仲裁法 §27。r3 短板 4 记录这六条全库无 statute_quotes，S3b 定向补注只覆盖已声明映射——窗口包就是把映射从"场景"提到"阶段"，落在 `lib/domains/labor.ts` 的 `windowPacks: Record<stage, packId[]>`，`retrieval.ts` 合并注入且不计入检索预算。

**版本与有效性**：沿用"复核触发条件"而非年度死刷新（beijing-shepin-fengding 范本）；每张核心法条卡 frontmatter 加 `verified_at` 与 `recheck_when`（如"最高法发布废止决定/人社局新通告"），`TODO核实清单.md` 只登记触发条件；校验脚本断言核心条 `confidence=原文核实`。

**可回溯链**：断言 → pack id（回复中方括号引用）→ `sources[]` → 官方 URL；MCP `citation_check` 工具与站内 CitationGuard 同一实现；用户自带 agent 场景下把 pack id 写进 `tubashu` 结构块（§15 D 路径）供服务端回填时二次核验。

**领域打包**：`knowledge/packs/<domain>/`，index 带 domain，跨域检索默认关闭（设计稿 §13）。

## Q3 推理层：按窗口分档的中间产物

法律方法进 agent 靠**结构化中间产物 + 程序化校验**，不靠加长提示。但中间产物按窗口分档，S0/S1 不做争点表——用户在会议室外五分钟，要的是"处境判定 + 三张卡"。

**一轮回答的中间产物清单**

1. 处境判定（服务端确定性）：stage × 窗口紧迫度（用户消息含"现在/马上/在会议室/今天必须签"等字面 + stage∈{风声,约谈中}）→ 进 `task-class.ts` 作为路由维度，也决定本轮是否启用争点表。
2. 档案读取确认（事实卡，已有）：本轮引用了哪些〔已核验〕、哪些〔用户自述待核实〕、哪些〔未记录〕要问。
3. 用户前提核验：用户陈述的法律前提（"不满一年没补偿""口头解除不算"）与窗口包相反时必须先纠正——进 outputDiscipline，判据剧本化。
4. 争点表（S4 仲裁准备及以后启用；S2 协商阶段可选）：每争点 = 要件 → 已有事实（引档案字段）→ 缺失事实 → 举证方（分清司法解释倒置 vs 仲裁规则证据偏在，r2 提醒）→ 依据 pack。落在个案报告 `disputes` 节（`registry.ts` ReportSectionSource 已有），领域包提供 `issueTemplates`（劳动：违法解除 2N/欠薪/未签合同双倍/年假），程序化校验每个要件对应事实卡字段 recorded 与否。
5. 风险区间而非结论：只允许"北京主流口径是…（引依据）/关键变量是 X"，禁止百分比胜率（字面表已有）。
6. 行动卡 ≤3（已有），S0/S1 首卡 due ≤24h（新断言）。
7. 落档写入清单：本轮该写的 timeline/claims/deadline/emotion，写入走幂等（Q5）。
8. 引用清单：本轮引用的 pack id 集合，供 CitationGuard 与 eval。

**拒答/转人工**：空包轮事前禁令（已有）；仲裁阶段自然分流律师——分流不是"劝找律师"，而是把 S4 的输出定义为"你自己办的材料清单 + 哪些点需要专业复核"；援助律师复核队列已存在（BOARD 有"援助律师会话"），争点表 `risks` 节固定一行"待律师核"。

## Q4 记忆与档案：三层记忆，来源打标

**三层**：事实卡（每轮服务端渲染，4600 字预算，P0 永不降级）→ 个案报告（长期记忆，agent 维护，服务端管过期，`report.ts`/`report-stale.ts` 已实现）→ 原件层（时间线、证据、文书）。事实卡是"服务端读出来的事实"，报告是"整理过的叙事"，两者分节不同（registry.ts 注释已说明），不合并。

**每轮先看档再答**：站内靠事实卡进 system prompt（已有）；MCP 靠 `case_facts` 首行状态区（报告过期 N 条变动 / 基本盘缺项 / 近 72h 危机标记）；无工具模式靠开场白携带事实卡 + 报告。补一条判据：陪跑模式开场必须有"前情提要"句（charter §4 末条，`intake.ts` 已注入指令，但无断言），夹具含 recentDone 行动卡 → 回复须提及"上次三件做了两件"。

**来源标注与核验状态**：现有〔已核验〕〔用户自述待核实〕〔未记录〕三态；补第四态〔第三方材料：evidence#id〕。落法：`timeline` 事件加 `source` 列（self / counterpart_doc / third_party / agent_inferred），事实卡按 source 打标，报告 `evidence` 节按 source 分组。用户自述与第三方证据的区分不是提示词问题，是列的问题——没有这一列，模型永远分不清"他说公司口头解除"与"解除通知书 OCR 结果"。

**用户自述可能是假的**：对抗输入的第一道防线就是"用户自述永远是待核实"，事实卡不允许把自述升为已核验；升级只能靠证据登记（evidence_register + extract）。

## Q5 工具面与执行：陪跑节奏由服务端驱动

**边界与幂等**：能力注册表 `lib/capabilities/registry.ts` 是唯一真源（现 ~55 能力，三入口共用）。读免费；写带 `client_ref` 或自然键去重（设计稿 §4.1）；spend 走报价 → 确认 → 扣费。**站内 `tools.ts` 的 timeline_add/action_card/claims_upsert 仍是独立实现**，要改为薄壳调注册表 handler，幂等才对站内生效（r3 短板 2 的根治）。

**陪跑节奏（本方案核心）**：节奏不由模型驱动，也不由用户 agent 轮询，由服务端定时任务驱动，模型只在用户回来时"接续"。三个机制：

1. 行动卡到期催办：扩展 `deadline-reminder.ts` 的扫描骨架（STAGES/notified_stages_json/Plan）到 `action_items.due_at`，档位当天 09:00 与逾期 1 天各一封中性通知（"你给自己定的三件事到期了，回来说一句做没做"），不发法律内容。
2. 期限触发器：`timeline_add` 落库后检查 kind/标题命中领域包 `deadlineTriggers`（已解除 → 仲裁时效；裁决签收 → 起诉 15 日；判决送达 → 上诉 15 日）且 deadlines 无对应行 → `markReportStale('缺期限')` + 事实卡首行"⚠ 有事件应对应期限但未登记"。模型下一轮必须处理，判据可测。
3. 前情提要接续：snapshot 已取 recentDone/openActions，加逾期统计；开场句判据化。

**用户自带 agent 与站内共用**：四条路径（§15）共用注册表；无工具模式的 `tubashu` 结构块回填走同一 handler，client_ref = 回填批次 id。陪跑节奏对四条路径一致，因为催办与触发器都在服务端。

## Q7 评测与验收

**判据集三层**：机械断言（`assertions.ts` 纯函数，产线同源）→ judge 两票制（`judge.ts`，不同家模型、SPLIT 交人工）→ 人审。**新增窗口剧本回放集**：S01–S03 扩为每个窗口 ≥5 变体（不同施压话术、不同情绪状态、含错误前提、含"要签了"），加 S0 风声阶段剧本（现无）。

**变异矩阵**：每个要件一条隔离负样本（"只差一条"而非"整体不合格"，r3 记录的人写负样本系统偏差）；正向存活样本必须并列（防字面表误伤如实句）。

**留出集**：真实脱敏对话回放需用户授权，暂无；替代是援助律师写的"真案改编"剧本，标注来源不进 judge 提示。

**评审模型偏差控制**：judge 与产线不同家（现 deepseek 判官、产线 relay claude/opus）；两票用不同模型；judge 看不到 pack 原文以外的"标准答案"；N/A 占比中间地带（r3 盲区④）改为逐项列出而非只告警 >50%。

**线上抽查**：每周抽 20 轮按 must/no 清单人审；三个自动指标日报：剥句率、行动卡缺失补救轮触发率（BOARD 09-04 待办）、期限触发器告警数。

**回归门禁**：红线剧本任一 FAIL 整场 FAIL；窗口剧本 must 项通过率 <90% 阻断发版。评测随领域扩展：剧本文件按 domain 分目录，共用断言函数，领域包自带最小剧本集（Q8）。

## Q9 模型策略

路由 = 任务档 × 套餐档（`routing.config.ts`）；本方案加一维"窗口紧迫度"：S0/S1 当场求助优先低延迟档，牺牲一点推理换首字时间。**不做微调**：数据量与幻觉证据（r1）都不支持，且微调会让判据失去同源性；靠检索 + 工具 + 确定性层（危机首段、期限算日、行动卡种子、封顶数据）。国产模型：judge 用 deepseek 合规；产线 relay 模型的 served_model 实付计价与 notice 留痕保持。离线兜底：模型不可用时仍能给确定性层——危机首段、期限倒计时、INTAKE_STAGE_ACTIONS 种子卡。

**用户自带 agent 场景（控制不了模型）**：质量不靠模型靠服务端——写入幂等与自然键、期限系统算日、`crisis_check` 与回填时二次过词表、`citation_check` 工具、事实卡首行状态区、催办与触发器在服务端、`tubashu` 结构块回填逐条预览确认。能拦的在服务端拦，拦不住的（说了什么）靠 skill 纪律 + agent_writes 抽查 + 网页展示层的核验标。
