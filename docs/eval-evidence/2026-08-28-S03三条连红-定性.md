## 一、为什么不能直接「在旧 SHA 上跑一批」

`run-batch.sh` 是 `git checkout <SHA>` **整棵树**。在 `06c6a3d` 上跑 S03，
**行为、判据、知识库三样一起回退**——量到的差异归因不了任何一样。

> **「换个 SHA 跑一遍」看起来是对照实验，实际是三个变量同时动。**

manager 给的另一条路（离线重放 / 读历史记录）才能把**判据钉死、只让行为变**。

## 二、开算之前的三道对齐检查（这一步定成败）

归档 + 本检出 `results/` 里有 **28 份 S03 转录（08-21 ~ 08-28）**。不能直接拿来比，先核：

| 检查 | 做法 | 结果 |
|---|---|---|
| **用户提问是否同一个** | 把每份转录的 `turns[0].input` 与当前 `scenarios.ts` 里 S03 的提问**逐字比对** | **27/28 逐字相同**，0 份不同，1 份空轮排除 |
| **条目原文是否全程未变** | 拿今天的三条原文当键去查；**并列出历史转录里所有含「条号/原文/来源」的条目做正对照** | 正对照只捞出**一种** G4 措辞 ⇒ 措辞没变过 |
| **知识库是否同一版** | `git diff --name-only` + 内容级 diff，`06c6a3d` vs `5dbca16` 的 `knowledge/` | **零差异** ⇒ 知识库这个协变量整个消掉 |

> **第一道用的是内容比对，不是 git 史推断。** 转录里没有行为 SHA 字段（`meta` 为 null），
> 但 `runNotes` 带着 `评测官定版批 <sha> 第N/M跑`——**先按内容确认可比，再用 runNotes 分组**，
> 顺序反过来就会拿一堆不可比的样本做出漂亮的分组表。

## 五、⚠️ 过程中我自己造了一次「统一、干净、完全错误」的结论（同族第十次）

G4 那一列**第一次算出来是「27 份全部未收录」**。

**病因**：我用正则从 `scenarios.ts` 内联数组里抠条目原文，
而 **G4 定义在 `G4_ITEM` 常量里、不在任何剧本的内联数组内** ⇒ 抠不到 ⇒ 键成 `None`
⇒ `byitem.get(None)` 对每一份都返回 None ⇒ **每一份都"未收录"**。

```
错误产物: UNIV-must-G4   —未收录— ×27      ← 整齐、无异常、可以直接写进报告
真实结果: FAIL 19 / SPLIT 5 / PASS 3
```

**发现方式**：抽取函数在同一次运行里**打印了它取到的原文**，G4 那行是 `(取不到)`。
——**让抽取器把它抽到的东西也印出来，是这一族最便宜的解药**：
`(取不到)` 与 `—未收录—` 是同一次失败的两个面，**印出前者才能不把后者当结论。**

> 与前九次的差别：**这次是在交出去之前抓住的。**

## 五之二、⚠️ 对照批撞出 `run-batch.sh` 一处根本缺陷：**它把自己的工具链也钉到被测 SHA**

对照批三跑全部完成、转录正常落盘，**但归档失败、且 HEAD 被留在游离态**。

```
FAILED       批次目录归档失败
META         无 head_restored_to
HEAD         06c6a3d（游离）
```

**病因**：`run-batch.sh` 的第一件事是 `git checkout <被测SHA>` **整棵树**。
而 `06c6a3d` **早于 `run-batch.sh` / `archive-batch.sh` 的引入**——
```
git cat-file -e 06c6a3d:scripts/eval/archive-batch.sh  →  不在 06c6a3d 中
ls scripts/eval/run-batch.sh（树在 06c6a3d 时）        →  没有那个文件
```
⇒ **脚本在运行途中把自己删掉了。**
`sh` 靠已打开的 fd 继续执行（inode 未释放），所以三跑照常跑完；
但归档段是**按路径**调 `archive-batch.sh`，那个文件已经不在 ⇒ 失败 ⇒ 写 FAILED ⇒ **在接回段之前退出**。

> **最刺的一点**：接回段我前后加固过三次（没接回 / 接回到旧地方 / 开批即游离）。
> **这三次加固全都假设脚本能走到那一行。这次是走不到。**
> **一个只在正常路径上执行的清理动作，不是清理动作。**

**修法（我的框架，已报备）**：接回改成 `trap ... EXIT`，让它在任何退出路径上都执行；
归档失败不再吞掉接回。**另：被测 SHA 早于工具引入时应当在开批前就拒跑并说明**，
而不是跑到一半发现工具没了。

**本次无损失**：转录三份完好（已备份 + 已补归档），树已手工接回 `ws/backend`，游离头上无提交。

## 六、⚠️ 第十一次：**差点把提交挂到线上 SHA 上面去**

写这份文件时批正在跑，`run-batch.sh` 已把树 `checkout` 到 `06c6a3d`、**HEAD 游离**。
我直接 `cat > docs/eval-evidence/…` —— **那个目录在 `06c6a3d` 上根本不存在**，写入当场失败。

**失败救了我一次，但设计上不该靠它**：若当时写的是一个两个 SHA 都有的路径，
提交会落在**以线上 SHA 为父**的游离头上，而 `git push origin HEAD:ws/backend` 照样成功——
**产物看起来完全正常，分支史却接错了地方。**

⇒ **规矩：批持有工作树期间，一切文档先落 scratchpad，等 `head_restored_to` 出现再提交。**
