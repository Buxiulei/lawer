昨日全天判据修法只有本机证据；CI 当晚上线，**首跑就抓到判据侧一条**。本文件是那条的闭卷。

## 一、CI 证据链（后台技术取，我照抄不改）

## ⚠️ 二、归因：**这条绿是两处修复叠加，不是我那一处**
`6c3abd14` 那次红的是完全另一件事（后台技术侧）：
```

  client.ts 的 DB_PATH 是顶层常量、import 那刻冻死；
  测试在 beforeAll 里设它再动态 import —— 只对同 worker 的第一个文件有效。
  而本机默认路径 app/data/lawer.db **恰好存在且被 gitignore** ⇒ 测试静默写进开发库，一路全绿。
```
修在 `608407d`（改成首次 `getDb()` 时求值）。

> **若记成「夹具改相对路径之后 CI 就绿了」，下次回溯的人会得到一个漏了一半的因果。**

## 三、我那条的形状（判据侧的账）
不是"路径写死"，是：
> **「对照物受控」与「被读的是受控那份」是两件事，前者不蕴含后者。**

我 `fb26a6c` 那条守卫承诺「判据依赖的对照物必须受版控」——**它做到了**，6 份夹具都跟踪着。
**断的是消费端**：测试用绝对路径读的是本机另一个检出的同名副本。
两份一致时什么都不暴露；**分叉那天，测试会对着没人 review 的那份继续报绿。**
更刺的一层：**那条强制受版控的守卫，自己写死了一个不受版控的位置。**

**已做成机检**：守卫扩一条「测试文件里不许出现本机绝对路径」。
变异预注册：改回绝对路径 ⇒ **红恰好 1 条（只有守卫）**，正对照与判决性实验**全绿**——
**「只红一条」正是这个 bug 的签名**：本机那个绝对路径存在，一切看起来正常，只有源级守卫看得见。

## 四、第二层：`vitest` 绿 ≠ 本机绿
我的第一版修复漏了一个局部 helper 的形参（`readFileSync` 运行时吃 `string | URL`，
所以**测试照跑照绿、只有 tsc 报**；而 CI 里 `tsc --noEmit` 排在 `vitest` 前面）。
**病因在我的改法上**：同批 4 处替换，**3 处带了「assert 目标串在场」，唯独"顺手那一处"没带**，
而 `str.replace` 不匹配时**静默 no-op、不报错**。
修完**回核了同批另外 4 处无 assert 的替换**——全部落地，**只有跳过自检的那处失败**。
⇒ 本机验证口径改为 **`tsc --noEmit` + `vitest` 两道**。

## 五、CI 上线半小时的三件事，性质完全相同（后台技术归纳，我认）
```
① 分支跑不到 main 上的守卫          （后台技术）
② 测试读的是本机副本，不是仓里那份   （我）
③ 测试静默写进开发库，因为目录恰好在  （后台技术）
```
**三个都是「你以为验的是 X，实际验的是 Y」，三个在报告上都长得像全绿。**
**没有一个能靠本机跑测试发现，全部需要干净检出。**
