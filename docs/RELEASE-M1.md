## 四、本轮拦下的问题（发版价值的实证）

今晚拦下并修复的、会直接伤害用户的缺陷：
1. **编造引用（第三态）**——真法条名 + 编造的子项内容，带引号冒充逐字原文。**用户会原样抄进书状、当庭念出来。** → 第五闸（引号内引用必须匹配本轮注入原文，否则改口"待核实"）。
2. **判例细节污染**——把用户自己的事实掺进判例案情。→ 模板拼装+字段分离。
3. **最低工资写死常量**——"今天算出来的数是对的，但是碰巧对"，北京调标即静默算错，受害者恰是最低薪群体。→ 从知识卡实时注入。
4. **核心法条选择性省略**——材料在手却只给条号，用户拿光秃条号上不了庭。→ 注入侧显式标注核心依据条。

## 五、判据体系的元教训（写给后来者）

**"表面信号良好、实质保障为零"的五种形态**：碰巧对的常量 / 碰巧过的正则 / 独立同源的错误 / 失灵的分类器 / 空集互比得"无变化"。共同点：**一个失灵的诊断器不会说"我坏了"，它会说"一切正常"。**

**判据设计双问**：①这条判据最省力的满足方式是什么？（防激励错位——"库内无原文判 FAIL"等于逼模型编原文）②这段文本里还有哪些信息我看见了但没用进判据？（防只看一层）

**红线的不对称**：同一个孤例，支持收紧就动手，支持放松就存疑——漏判伤用户，误判只伤效率。

**账要记对地方**：把账记到该记的地方，而不是让模型在"编造"与"被判挂"之间二选一。

### 6.2 归因教训（写给后来者，也写给我自己）

**我们差点把"模型选择性省略"记在模型头上，真相是那条指令根本没发出去。**
**归因错了，就会去修一个没坏的东西，同时留着真正坏的那个。**

manager 本轮四次栽在同一族问题上：只看正文即裁定红线 / 只看检索即归因 / **凭空合成一个不存在的 SHA 并签收** / 在两个来源尚未交叉确认前签发终局结论。
由此立的硬规矩：**凡终局结论，签发前必须确认所有相关方对同一批次的读数一致；凡写出具体标识符，必须当场验证或注明出处，否则写"待确认"。**

### 6.3 恢复后修法包（四项，按序）

1. **共用条号归一函数**（行为面 coreArticleKeys + 判据面 normalizeArticle **同源**，正反样本齐）→ **必须重跑**
2. 四态加"有原文未结构化" + body 命中检测（判据侧）→ 离线重打分
3. 「替决」判据措辞对齐 §7.2 终裁（已批，含留痕注释与两个负样本）
4. **首诊场景核心条来源设计（本轮真因，优先级最高）**——⭐机制依赖档案已建，而**首诊恰恰是档案最空、用户最没判断力、最需要正确引用的时刻**。→ 专议，manager 参与；修好前首诊场景 G4 按"⭐机制不可用"处理，不判 FAIL。
   > 执行代理自查原话（入档）：**「我把'不猜'和'首轮完全没有指引'当成了同一件事——不猜 ≠ 什么都不给。」**
   > 这条是本轮最深的设计教训：**一个为了"不臆断"而设计的沉默，在用户最需要指引的场景里变成了失职。**

### 6.4 正向档

- 模型在给出法条原文时**主动带出该卡的"待核实"状态标签**——诚实链条完整到了可信度标签这一层。
- ws2-agent **主动推翻自己两小时前已被上游采信的结论**，并自标为自己所立规矩的二次应验。评语：**推翻自己比推翻别人难得多，尤其在结论已被采信之后；这种自证其罪式的严谨，是这个项目质量的真正来源。**
