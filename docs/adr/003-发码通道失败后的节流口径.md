## 背景

工单 F-204（major）原文两句，在「基座没有短闸」这个前提下互相不自洽：

1. 要求：「冷却与当日配额只在**通道确认发出**后记；失败不占（**允许保留一个 ≤5 秒的防连击闸，
   若已有就复用**）」
2. 判据：「注入通道失败 → **立即重发**不被 60 秒冷却拦、当日计数不增」

基座 487b6ef **没有任何短闸**——「若已有就复用」在本仓没有对应物。于是第一句能读成两种：
「允许**保留**已有的」（⇒ 没有就不新建）或「允许**有**一个」（⇒ 可以新建）。
两种读法在判据上分叉：新建短闸后，「立即重发」就必然要改写成「5 秒后重发」。

同时 24acdb0 的修法本身开了一个真缺口：失败不再落行 ⇒ 60s 冷却不成立；而出口 IP 那条计数
对 `knownUser=true`（存量用户登录）**整条豁免**。两者叠加 ⇒ **存量用户 + 通道持续报错 = 零节流**，
按住重发就是对上游的无限重试。这是 A 案存在的理由，B 案下它是一个如实登记的已知缺口。

## 争点

新建一张表（`otp_send_attempts`）+ 一个新错误码（`SEND_TOO_FAST`）+ 改写工单写死的判据，
是否在工单授权范围内。

## A 案：采纳 ≤5 秒防连击闸

- 落地物：`otp_send_attempts` 表（migrate 第 49 张）、`SEND_TOO_FAST` 错误码（429，retry_after=5）、
  `checkSendQuota` 末位新增第四道闸、判据由「立即重发放行」改写为「1 秒后撞 SEND_TOO_FAST、
  第 5 秒准点放行」。手机侧与邮箱侧共用一张表、共用一道闸。
- 代价：改契约（新表 + 新错误码，前端要认 `SEND_TOO_FAST` 才不会把它当成 60 秒冷却显示）；
  `migrate.ts` 属数据表管理地盘，需按看板规矩知会；工单判据被改写。
- 收益：堵住上面那个「存量用户 + 通道持续报错 = 零节流」的缺口。
- 合并动作：**a52c319 按现状合并**，无需再改代码。

## B 案：维持工单原判据「失败后立即重发放行」

- 落地物：撤掉短闸全部三处（表 / 错误码 / 闸），判据恢复「同一秒立刻重发就能成」；
  38f2b8e 里与短闸无关的两项**保留**——当日上限边界那条判据（9 成功 + 1 失败 + 第 10 次成功
  → 第 11 次仍被拒），以及 `otp.ts` 那句不成立注释的更正（改成如实登记缺口，不再宣称
  「拦无限重试的是出口 IP 那条计数」）。
- 代价：上述缺口保持敞开，需另立工单补。
- 收益：不动契约、不改判据、不碰 `migrate.ts`。
- 合并动作：在 a52c319 上 `git apply` 现成补丁
  `scratchpad/rd-qa2-otp/fix-optionB.patch`（6 文件 +36/−253，`git apply --check` 已过）。
  实测：`tsc` EXIT=0；`vitest` 全量 **4098 passed / 9 skipped**，EXIT=0；
  变异 M1（记冷却挪回发送前）5 failed、M4（失败仍计配额）5 failed、R1（撤行去掉 WHERE）2 failed，
  三臂全红。日志见 `fix-optionB-*.log`。
- **补丁若已随 scratchpad 消失，B 案可只用 git 重建**（上面那份补丁就是这么造的）：
  1. 把这 6 个文件取回 650dc2e 版本 —— `git checkout 650dc2e -- app/src/lib/auth/otp.ts
     app/src/lib/db/otp.ts app/src/lib/db/migrate.ts app/src/lib/db/__tests__/migrate.test.ts
     app/src/lib/auth/__tests__/otp.test.ts app/src/lib/auth/__tests__/email-register.test.ts`；

     「9 次成功 + 1 次失败 + 第 10 次成功 → 第 11 次仍被当日上限拒（F-204 / R1）」，
     其中失败后那次重发写回**同一秒**（`at(540)`，B 案下无短闸即刻放行）；
  3. `otp.ts` 的 `sendPhoneCode` 文档注释里那句「上游持续报错时拦住无限重试的是出口 IP 那条计数」
