## 一、格式

- 一行一个 JSON 对象（JSONL），UTF-8。
- **键名用中文，照外勤现有输出原样给**。映射写在导入侧（`ingest.ts`），
  外勤不必为我们改格式——那是另一条工具链，改它意味着它每次升级我们都要跟着改。
- 坏行（不是合法 JSON）不静默跳过：CLI 逐行报出行号与原因，其余行照常导入。

## 二、现有必给键（D18 实产的 13 个键）

| 键 | 落到哪一列 | 规则 |
|---|---|---|
| `案号` | `case_no` | **唯一必填**。空串/空白 ⇒ 拒收该行并报出行号 |
| `审理机关` | `court` | 空串 ⇒ NULL |
| `程序` | `stage` | 见 §四映射表；表外取值 ⇒ NULL（**不猜**） |
| `案由` | `cause` / `is_labor` | 空串 ⇒ NULL；含「劳动争议」⇒ `is_labor=1` |
| `裁判主文_逐字摘录` | `summary` | **逐字原文**，套路归纳的引文核验以它为靶子 |
| `原文获取状态` | `has_fulltext` | `已取全文` ⇒ 1；`仅列表项_*` ⇒ 0；**其它取值 ⇒ 0 并报警告** |
| `主体归属` | —（不入列） | 不以「命中」开头的行**整行跳过**，计入 `skippedNotSubject` |
| `标题` / `年份` / `全文字数` / `检索式` / `归属依据` / `金额_摘自主文` | —（不入库） | 见 §三 |

## 三、刻意不落库的键，以及为什么

| 键 | 为什么不落 |
|---|---|
| `年份` | **年份不是日期**。拿它填 `judged_at` 会让「2023 年某天」变成一个精确日期，而时长统计正是按这两个日期算的 |
| `标题` | 标题足以让模型脑补案情。仅列表项的行**连标题都不喂**给归纳模型（§1.3 输入白名单） |
| `检索式` | 「宜信-全文劳动争议」是**检索条件**，不是案由。拿它填 `cause` 等于把我们自己的搜索词写成法院认定的案由 |
| `金额_摘自主文` | 数组里是主文里的金额串（含「元」「万元」混排）。解析成分要做单位推断，推断出来的钱数会以一个精确的整数落库，读的人无从分辨它是猜的。需要金额请改用 §五 的 `判付金额_分` |
| `全文字数` | 与 `has_fulltext` 重复，且不参与任何判据 |
| `归属依据` | 归属判定由外勤做完，导入侧只执行不重判 |

## 四、`程序` → `stage` 映射

| 外勤取值 | `stage` |
|---|---|
| `民事一审` / `一审` | `一审` |
| `民事二审` / `二审` | `二审` |
| `仲裁` | `仲裁` |
| `执行` | `执行` |
| `民事再审` | **NULL** |
| 空串 / 其它 | **NULL** |

`民事再审` 刻意不映射：再审不属于四段时长的任何一段，硬塞进「二审」会污染二审样本。
需要再审段时请先来谈第五段怎么定义，不要在映射表里悄悄加一行。

## 五、可选扩展键（外勤取到全文并逐字读过之后才会有）

**这些键决定了统计能不能出数**。现有 155 行一个都没有 ⇒ `docs_outcome_decided = 0`
⇒ 统计层判「样本不足」⇒ 文书块自动全额退款。这不是 bug，是红线按设计生效。

| 键 | 落到哪一列 | 规则 |
|---|---|---|
| `裁判日期` | `judged_at` | 文书上**载明**的日期（ISO `YYYY-MM-DD`）。推断的一律不给 |
| `立案日期` | `filed_at` | 同上。执行段请填「判决生效日」，`裁判日期` 填「执行立案日」 |
| `结果` | `outcome` | 只认三值：`劳动者全部获支持` / `劳动者部分获支持` / `劳动者未获支持`。**其它取值 ⇒ NULL 并报警告**（不静默兜底成某一档） |
| `结果依据_逐字` | `outcome_basis` | 支撑上面那个判定的**逐字原文**。没有它，`outcome` 就是一个没人能复核的断言 |
| `申请人方` | `applicant_side` | `劳动者` / `单位`。**与结果分开看**：实测某系公司 2022-09 有一批「用人单位起诉员工」的案子，此时「公司赢了」与「劳动者输了」不是同一件事 |
| `判付金额_分` | `amount_awarded_fen` | 整数，**单位分**。非整数 ⇒ NULL |
| `全文文件路径` | `fulltext_path` | 全文落盘位置（可选） |
| `采集时间` | — | 暂不读；采集时点走 CLI 的 `--fetched-at`（见 §六） |

## 六、导入命令

```bash
cd app
npx tsx ../scripts/ingest-dossier.ts \
  --file /home/roots/裁员应对员/user-case/company-watch/litigation/D18-宜信系劳动争议判例清单.jsonl \
  --dossier 1 --profile 7 --fetched-at 2026-08-28          # 干跑，只算不写
npx tsx ../scripts/ingest-dossier.ts ... --apply            # 真写
```

- **默认干跑**：写库不可撤销，必须是显式要求的那一次。
- `--fetched-at` 是**采集**时点，不是导入时点。统计卡的 `as_of` 用它——
  拿导入那一刻冒充采集时点，会把三个月前的旧数据显示成今天的。
  重导已有条目时 `fetched_at` **不更新**（`INSERT OR IGNORE` 只管新增），
  于是 `as_of = MAX(fetched_at)` 记的是「最后一次**采到新东西**是哪天」，
  而不是「最后一次重跑导入是哪天」。方向是保守的那一侧：没采到新的，数据就不该显得更新。

### 实产冒烟（2026-08-31，155 行全量）

```
读入 155 行：新增 89、已存在 0、主体未命中跳过 66、拒收 0
统计：docs_total=89  docs_fulltext=32  docs_outcome_decided=0  as_of=2026-08-28
```

⇒ 现有语料 **`docs_outcome_decided = 0`**，统计层判「样本不足」、不出任何比率。
这不是管线没跑通，是 §五那批可选键一个都还没有。要出比率，外勤得先把
`结果` / `结果依据_逐字` / `申请人方` 三个键补上（并且只能来自逐字读过的全文）。
- `--profile` 是 `company_profiles.id`。之所以必填，见 §七。

## 七、两处已知的结构债（请 manager 知悉）

1. **`company_litigation.company_profile_id` 是既有的 NOT NULL 列**，而判例数据在语义上
   属于**档案**（跨案共享）而不是**案件主体**（案件私有、随案件 `ON DELETE CASCADE`）。
   改成可空要重建表，卡在「迁移框架无事务」那笔 WS1 递延债上。
   现状的后果：**第一个买家删掉自己的案件，这份档案的判例行会被级联删掉**。
   兜底不是修复，只是不让它变成静默错误——`lookupCache` 会比对
   「实际入档条目数 vs 统计快照 docs_total」，对不上就不命中缓存、按重采处理
   （判据在 `lib/company/__tests__/dossier.test.ts`）。
2. 去重因此要靠两把唯一键并存：`uq_company_litigation`（案件维度，既有）与
   `uq_company_litigation_dossier`（档案维度，本次新增的部分唯一索引）。
   少了后者，同一份 JSONL 挂在同一档案的两个 profile 下导入会让 `docs_total` 翻倍——
   而那个数是比率的分母之一。

## 七·补、关联谱系（`graph.json` → `company_profiles`/`company_relations`）本轮**不做**，交界给谁

本契约只覆盖**涉诉 JSONL → `company_litigation`**。关联谱系的导入（外勤 `graph.json` 的
`nodes[]`/`edges[]` → `company_profiles`/`company_relations`）**本轮刻意不实现**，不是漏了——
它有四处得先定的边界，硬做会做错或串味：

1. **`role` 会被覆盖**：唯一的主体 upsert 入口 `lib/db/agent.ts:upsertCompanyProfile`
   对 `role` 是**无条件覆盖**（`role = ?`），而 `graph.json` 的 `node.role` 是描述串
   （「现用人单位/目标主体」），落不进 `company_profiles.role` 的枚举（签约/用工/关联）。
   复用它会把 agent 在问诊里定的 `role` 冲掉；另写一个 upsert 又违反「company_key/主体只有一个入口」。
   ⇒ 要么把 `upsertCompanyProfile` 的 `role` 改成可选 + `COALESCE`（向后兼容，agent 一直传 role 故不变），
   要么给谱系节点单独的落库口——这是**入口归属**决定，不该由采集导入面单方拍。
2. **`tier` 没家**：`node.tier`（圈1/2/3）语义属 `company_watches.tier`（监控圈层），是**守望盯梢那条线**的地盘，
   不是本导入面的列。谱系导入若顺手写 tier 就串进了监控计费/衰减规则。
3. **`GraphNode` 是拼出来的视图，不是一张表**：`litigationCount` 由 `company_litigation` 计数、
   `eventCount` 由 `company_watch_events` 计数、描述 `role`/`tier` 各有别处——
   `_mock/company-graph.ts` 那个形状是 `GET /api/v1/cases/:id/company-graph` **读侧 JOIN** 出来的，
   不是 `company_profiles`+`company_relations` 两张表能直存的。读侧端点尚不存在（现为 mock），
   没有它无法验证导入的往返正确性，而端点属图谱 UI 那条线。
4. **案件维度耦合债**（见 §七-1）：`company_profiles`/`company_relations` 都是 `case_id NOT NULL`、
   随案件级联删。谱系是**公司维度**资产却只能挂在案件私有表上，与 `company_litigation` 同病。

**边可以直存的部分**（留给接手的人，判据已想好）：`edges[]` 的 `relation` **逐字原样落库**
（`_mock` 的 `GraphEdge.relation` 注释即「关系原文」，不要映射成枚举，映射就是推断）；
`confidence` 只认 `高`/`中`/`低`，**其它取值报警告不静默兜底成「中」**（兜底即编造置信度）；
`from`/`to` 指向 `nodes[]` 里不存在的 id 的**悬挂边**要报出来、不静默丢（丢一条边＝丢一条外勤断言的关系）；
再导入幂等靠 `(case_id, from_profile_id, to_profile_id, relation)` 应用层去重（这两张表没有天然唯一键）。

## 九、免费前置探测载荷（`company_probe_cache.payload_json`）

免费前置探测（§2.3）在**扣费之前**免费返回四个数字 + 一行工商状态，把「必定有货」从承诺变成
扣费前可验证的事实。四个数字是**采集侧数出来的客观计数**——**零 LLM**，app 侧只读不算。

- 实现：`app/src/lib/company/probe.ts`（读缓存 / 限流 / 降级）、写入口 `upsertProbeCache`（先体检再落库）。
- 缓存键 = `companyKey`（uscc 优先，缺则归一化名称，与档案同一把键）；`fetched_at` 记的是
  **我们这份拷贝的入缓存时刻**（TTL `dossier.probe_ttl_hours`，默认 24h），**不是数据的 as_of**。
- 限流：登录后每用户每日 `dossier.probe_free_per_day`（默认 2）次；**只有一次真采集占配额**，
  缓存命中免费不限次。配额耗尽即降级为「仅缓存命中」并如实告知——**不报错、不返回空**
  （空会被读成「查无此公司」）。采集器未接入时同样如实降级（`no_collector`），不静默。

外勤采集侧需产出的 `payload_json` 形状（`ProbePayload`）：

| 字段 | 含义 | 体检规则（不过则拒收、不写缓存、不占配额） |
|---|---|---|
| `entity_matched` | 主体命中与否 | 为 `false` 时四个计数必须全 0（未命中就没有可归属的记录） |
| `entity_name` / `uscc` | 命中的规范全名 / 统一社会信用代码 | 未命中为 `null` |
| `gs_status` | 工商状态一行：存续/经营异常/已注销/简易注销公告中 | 明细在 M2 |
| `relation_count` | 关联主体数（明细在 M3） | 非负整数 |
| `relation_breakdown` | 如 `{股权:3, 同法代:1, 同址:1}` | 可选 |
| `litigation_count` | 涉诉记录数（明细在 M4） | 非负整数 |
| `labor_count` | 其中劳动争议数 | 非负整数、**≤ `litigation_count`**（是其子集） |
| `doc_url_count` | 其中有公开文书链接的篇数（M5 可售性判据：<5 置灰不卖） | 非负整数、**≤ `labor_count`** |
| `as_of` | 采集时点 | **必填**（缺了四个数字就是四个悬浮的数，同统计层 as_of 红线） |
